# Database schema

The ordered migrations define colleges and approved email domains; Auth-backed profiles; categories; moderated listings and private photos; bookings and status history; conversations, messages and notifications; reports and disputes; reviews; payments, webhook idempotency, deposits, refunds, late fees, overdue-job idempotency, administrator audit logs, and campus-scoped security events. Payment, deposit, and refund records are distinct. Test-mode deposit refund requests are created only for a captured payment after a completed booking; administrator review is audited and a provider refund reference is required before the deposit can be marked refunded. Listing and booking reports are submitted through a role-checked API and reviewed through an audited administrator workflow. Approved listings can be archived by campus administrators with a reason; removal is blocked while open bookings exist and preserves all listing, booking, photo, and financial records. Security events store a fixed event type and source, actor, severity, status, hourly occurrence count, and review note; they do not store IP addresses, emails, tokens, or raw payment data.

UUIDs are used for primary keys. Monetary amounts use fixed-precision INR values. Booking prices are snapshots. PostgreSQL exclusion constraints prevent overlapping accepted or later reservations for a listing; status checks reject invalid lifecycle jumps. The booking workflow migration adds service-role-only functions for creating priced requests and participant-checked transitions. Those functions record status history and notifications in the same transaction. Message sending, listing moderation, reports, fee review, overdue checks, and security-event recording/review use service-role-only functions; admin decisions write audit entries. Security event inserts are restricted to fixed server-side event codes and campus membership is derived from the actor profile. Repeated events from an account and source are grouped for one hour. The overdue job stores one run claim per booking and date and one separate calculated fee per overdue day, allowing safe retries and catch-up after a missed run. All application tables have RLS enabled. Public reads are limited to categories and approved listing records; private operations use the API and its verified authorization checks. The item photo bucket is private with a 5 MiB size limit and a restricted image MIME allowlist.

Apply migrations to a linked Supabase project with `npx supabase db push`. For a fresh local project, install Docker Desktop, run `npx supabase start`, then `npx supabase db reset`. `db reset` recreates local data, so use it only for local development. The `seed.sql` file contains catalog rows only; it contains no student records. All 10 migrations passed an ordered PostgreSQL 18 run using minimal Auth and Storage compatibility schemas; Supabase-specific behavior still needs verification against the selected project.
